Lets use this as the development workflow. This should be persisted so other agents can us it.

1. Inspect the repository, current Git state, and applicable instructions before making changes. Preserve unrelated staged, unstaged, and untracked work.
2. Create a branch before making code changes.
3. Work in TDD style when behavior or structure is testable:
   - Add or update a focused test before implementation.
   - Confirm the test fails for the expected reason.
   - Implement the smallest appropriate change.
   - Run focused tests while iterating.
4. Inspect the complete diff and remove accidental or unrelated changes.
5. After the main agent completes an implementation pass, run the `ui-review` sub-agent before verification. The `ui-review` sub-agent is an expert at design and websites. Address every actionable `ui-review` finding before running the `verifier`.
6. Run the `verifier` sub-agent to perform the appropriate builds and tests for the change. The verifier reports failures, flakes, missing coverage, and environment issues. Fix or explicitly resolve every actionable finding before starting code review. If a verifier finding requires a code change, rerun the verifier after addressing it.
7. Before every commit, run a`code-review` sub-agent against the current branch diff and all staged, unstaged, and untracked files. Address every actionable finding before committing. The code review sub agent should be an expert in the languages and frameworks for the app.
8. Commit using the Conventional Commits format after verification and code review are complete.
9. When creating a pull request:
   - Confirm that local verification remains valid.
   - Rerun the `code-review` sub-agent only if the reviewed state changed after the pre-commit review. A changed state includes code, tests, documentation, generated files, conflict resolution, or any other staged, unstaged, or untracked content.
   - Do not repeat code review when the already-reviewed diff and worktree remain unchanged.
   - Push and create the pull request only after local verification and any required code review are complete.
10. Merge a pull request only after GitHub reports a clean merge state and all configured checks pass. Self-merges are allowed when those conditions are met.
