### 7. Concurrency — safe, and I proved it rather than reasoning about it

Three interleavings driven directly against Postgres at READ COMMITTED, bypassing the application lock entirely:

- **Cancellation commits between a rival's occupancy check and its insert** — the rival's insert is accepted. Correct: the seat genuinely is free. The stale read said "occupied", so the application would have refused — a spurious rejection, never a double sale.

- **Rival inserts while the cancellation is still uncommitted** — T2 blocks; T1 rolls back; T2 is correctly rejected `23505` and the original holder keeps the seat. No phantom, no lost release.

The partial index behaves identically to the unconditional one over the held-row set. This is the load-bearing result and it holds.

**But** the E2E contested-seat test tests the lock, not the index. `/home/scottdensmore/Developer/scottdensmore/travel-app/e2e/booking-authority.spec.ts:33` starts from an empty flight; with the flight lock held, the loser's occupancy check alone rejects it, so the test would pass with no unique index at all — consistent with the partial-index mutation killing only Jest database tests, none of the E2E. ## Findings, most severe first

### 1. REGRESSION — two flights of one itinerary changing status concurrently leave the booking `CONFIRMED` on a cancelled flight

**27 of 30** unassisted rounds — a plain `Promise.all` of two `updateFlightStatusAction` calls, no artificial blockers. With the two flight locks held and released together, 17 of 25.

Setup: booking on legs A+B, A already `CANCELLED` (booking `DISRUPTED`), B operating. Concurrently reinstate A and cancel B. Final state observed: booking `CONFIRMED`, flight B `CANCELLED`.

Mechanism, under READ COMMITTED with each transaction holding only *its own* flight's lock (`/home/scottdensmore/Developer/scottdensmore/travel-app/app/actions.ts:1053`):

- cancel-B's `updateMany` filters `status: 'CONFIRMED'`; its statement snapshot still sees the booking as `DISRUPTED`, so it does not match and is never row-locked — no blocking, no serialisation.
- reinstate-A's `updateMany` evaluates `NOT: { legs: { some: { flight: { status: 'CANCELLED' } } } }` against a snapshot where B is still `ON_TIME` (cancel-B uncommitted), so the sibling guard passes and the booking goes `CONFIRMED`.

Both commit. Sequentially, in *either* order, the outcome is correct — this only appears concurrently. The lock is correct for the flight it takes; the predicates read rows belonging to flights it does not lock. Result is precisely the defect the slice exists to remove: a live boarding pass on a flight that is not operating, no `DISRUPTED` history row, no notification, and the customer later pays the 20% Economy fee to cancel.

### 2. REGRESSION — the mirror: reinstating both legs at once strands the booking `DISRUPTED` while both flights operate

**19 of 20** rounds. Booking `DISRUPTED` on A+B, both cancelled; reinstate both concurrently: each `updateMany`'s sibling guard sees the other flight still `CANCELLED`, both skip, booking stays `DISRUPTED` with both flights `ON_TIME`.

Same root cause. Worse to recover from than #1: the admin select already reads `ON_TIME`, so no `onChange` fires and staff cannot repair it without deliberately toggling to `CANCELLED` and back. Meanwhile the profile offers the customer "Cancel for a full refund, with no cancellation fee" on two flights that are running — a real refund on an undisrupted trip.

Both #1 and #2 need two overlapping status changes on two legs of one itinerary. Each row in `/home/scottdensmore/Developer/scottdensmore/travel-app/app/admin/flights/FlightStatusSelector.tsx` has its own `useTransition` and disables only its own `&lt;select&gt;`, so one admin changing two rows, or two admins, is enough.

### 3. REGRESSION — a `DELAYED` flight no longer notifies anybody holding a confirmed booking

Verified against the database: `updateFlightStatusAction(flight, 'DELAYED')` on a flight with a `CONFIRMED` booking produces **0 notifications**.
