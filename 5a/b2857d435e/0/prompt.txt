### 6. Observation — the backfill guard is unreachable through the schema's own constraints

`SeatAssignment.legId` → `ItineraryLeg(id, flightId)` FK; `ItineraryLeg.bookingId` is `NOT NULL` FK to `Booking`; `Booking.createdAt` is `NOT NULL`. The `COALESCE` fallback therefore cannot return NULL and `stranded` cannot exceed 0. I could only make it fire by dropping `SeatAssignment_legId_flightId_fkey` first. Belt-and-braces is defensible, but note the message is the wrong diagnosis for the failure mode that *can* actually reach it: when I deleted the backfill `UPDATE`, the guard correctly refused the deploy but reported *"Their legs have no booking, which should be impossible"* for two rows whose legs were perfectly fine.

### 7. Concurrency — safe, and I proved it rather than reasoning about it

`lockFlightForUpdate` still covers the new path. All four seat-mutating entry points take the `Flight` row lock, including `cancelBookingAction`, and the trigger's `UPDATE` runs inside that same locked transaction — so the release is at least as well serialised as the old rename. The lock coverage is in fact *stronger* than before: the fact now lives on the row the index covers, rather than on a `Booking` row that the flight lock never protected.

Three interleavings driven directly against Postgres at READ COMMITTED, bypassing the application lock entirely:

- **Cancellation commits between a rival's occupancy check and its insert** — the rival's insert is accepted. Correct: the seat genuinely is free. The stale read said "occupied", so the application would have refused — a spurious rejection, never a double sale.
- **Two rivals both take the freshly released seat** — T2's insert blocks on the partial index while T1 is uncommitted, then fails `23505 duplicate key value violates unique constraint "SeatAssignment_flightId_seatNumber_held_key"`. Exactly one held row survives.
- **Rival inserts while the cancellation is still uncommitted** — T2 blocks; T1 rolls back; T2 is correctly rejected `23505` and the original holder keeps the seat. No phantom, no lost release.

The partial index behaves identically to the unconditional one over the held-row set. This is the load-bearing result and it holds.

**But** the E2E contested-seat test tests the lock, not the index. `/home/scottdensmore/Developer/scottdensmore/travel-app/e2e/booking-authority.spec.ts:33` starts from an empty flight; with the flight lock held, the loser's occupancy check alone rejects it, so the test would pass with no unique index at all — consistent with the partial-index mutation killing only Jest database tests, none of the E2E. Its comment ("SeatAssignment's unique index is now the sole guard against selling a seat twice") overstates what it verifies. And no test anywhere contests a seat that a cancellation just freed — the race this change actually creates.

### 8. The reversal works, with one undocumented hazard

Verified end to end against a database holding both a released `14B` and a live `14B` on the same flight: reversal succeeded, reimposed the placeholders (`14B` → `CANCELLED-p4`, lossy as documented), recreated the unconditional index, and `migrate deploy` re-applied cleanly afterwards, re-deriving correct release dates from `BookingStatusChange`.

Not documented: `'CANCELLED-' || "passengerId"` is only unique per flight if a passenger holds at most one released assignment per flight. An itinerary with two legs on the same flight would produce a duplicate and the `CREATE UNIQUE INDEX` would fail. The `BEGIN`/`COMMIT` wrapper makes that safe — the whole reversal rolls back — but it is worth a line in the header comment, since the reversal is the one place the header promises to have thought this through.
